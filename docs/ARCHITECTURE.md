# Устройство программы

## Главное решение

Ядро не знает о Windows. Сопоставитель, каталог, счёт плана, состояние,
журнал и карантин работают на любой системе; всё, что правит реестр,
запускает `netsh` и `sc`, живёт за одной границей — `enforce/windows/`.

Так сделано не ради переносимости: программа нужна только на Windows.
Причина в другом. Самая ответственная часть программы — решение «пускать или
нет» и счёт того, что именно попадёт в реестр, — иначе проверялась бы только
вручную и только на настоящей машине, где ошибка стоит дороже всего. Сейчас
эти проверки гоняются на любой машине, в том числе на Ubuntu в сборке.

```
strazh/
├─ core/          ядро: типы, каталог, сопоставитель, состояние, журнал
├─ enforce/
│   ├─ plan.py    счёт плана: каталог → список операций (без системы)
│   ├─ dryrun.py  распорядитель, который считает план и ничего не меняет
│   └─ windows/   единственное место, где есть реестр, службы и брандмауэр
├─ watch/         наблюдатели за процессами и загрузками
├─ gui/           окно
├─ app.py         прикладное ядро: точка сборки всего
└─ cli.py         командная строка
```

## Поток решения

```
файл или процесс
      │
      ▼
  FileFacts ─ имя, исходное имя из ресурса версии, издатель, сумма, путь
      │
      ▼
  Matcher.evaluate()          ← скомпилированный каталог + исключения
      │
      ▼
   Verdict ─ пускать или нет, по какому признаку, из-за какой цели
```

`FileFacts` — отдельный тип не случайно: он развязывает сопоставление и
способ добычи сведений. В бою их даёт разбор PE-заголовка, в проверках —
литерал в три строки.

Порядок проверки внутри `Matcher` выбран так, чтобы переименование не
спасало и чтобы дорогое считалось последним:

1. неприкосновенное имя — пропустить сразу;
2. исключения человека;
3. контрольная сумма (если уже посчитана);
4. точное имя файла — поиск по словарю;
5. исходное имя из ресурса версии — **ловит переименование**;
6. маски имён;
7. издатель и название продукта — **ловят переименование**;
8. путь.

## Поток применения

```
Catalog.enabled()
      │
      ▼
  plan.plan_*()  ─ список операций: какой ключ, какая маска, какая служба
      │
      ├─ WindowsEnforcer  → правит реестр, службы, брандмауэр, hosts
      └─ DryRunEnforcer   → только пересказывает план
      │
      ▼
   State  ─ что именно изменено и что было раньше
      │
      ▼
  revert()  ─ откат ровно по этому списку, а не по догадкам
```

Счёт плана отделён от исполнения ровно поэтому: `apply --dry-run` и
настоящее применение считают **один и тот же** план. «Показать» и «сделать»
не могут разойтись.

## Почему tkinter

У программы, которая ставится с правами системы, каждая внешняя зависимость
— это ещё один способ ей навредить. Tkinter входит в состав Python и не
тянет за собой ничего. Цена — вид описан руками в `gui/theme.py`; это
показалось честным обменом.

## Почему события, а не опрос

Первая версия опрашивала список процессов раз в секунду. Это работало и
стоило процентов процессора круглые сутки — на машине, где ничего не
происходит. Плата бралась постоянно, а польза появлялась только в тот
момент, когда что-то запускалось.

Теперь Windows рассказывает о запуске сама: событие `Win32_ProcessStartTrace`
приходит в момент создания процесса. В простое поток наблюдателя стоит на
очереди и не просыпается ни разу. Выигрыш двойной — узнаём о запуске не через
полсекунды в среднем, а через миллисекунды, и нежелательная программа не
успевает показать окно.

Подписка сделана через PowerShell, а не через `pywin32`. Причина не в
удобстве: программа работает с правами системы, и лишняя зависимость в ней —
лишний способ ей навредить. Нужный код умещается в двадцать строк, которые
видно целиком в `watch/procevents.py`.

Опрос никуда не делся — он остался запасным источником для машин, где
подписка не поднимается: без прав администратора, на урезанной сборке, при
выключенной службе WMI. Наблюдатель об этом не знает: оба источника кладут
события в одну очередь. Какой из них работает, видно в окне и в журнале —
молча деградировать в худший режим программа не должна.

Раз в пять минут делается полная выборка. Это страховка от пропущенного
события, а не рабочий режим: пять минут между проходами не создают заметной
нагрузки, но не дают пропущенному запуску остаться незамеченным навсегда.

## Обход папок

Наблюдатель за загрузками пользуется `os.scandir`, а не перечислением с
последующим опросом каждого файла: на Windows сведения о размере и времени
приходят вместе со списком, и отдельного обращения к диску на каждый файл не
нужно. Перед обходом проверяется время изменения самой папки — если она не
менялась, читать её содержимое незачем. Это важно для временной папки, где
бывают десятки тысяч файлов, а обход идёт круглые сутки.

## Три собранных файла

Windows не даёт совместить окно без консоли и работающую командную строку в
одном исполняемом файле: у программы, собранной без консоли, нет потока
вывода. Отсюда `Strazh.exe` (окно), `strazh-cli.exe` (командная строка) и
`strazh-deny.exe` — обработчик, который запускается вместо каждой
остановленной программы и потому собран отдельно и мелким.
